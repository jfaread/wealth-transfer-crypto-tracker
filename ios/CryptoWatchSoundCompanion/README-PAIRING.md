# Native XRP sound companion - staged release checklist

**Status (15 November 2026): development branch only; not installed or sending production APNs notifications.**

The goal is the original **XRP Alert** two-tone sound on iPhone, including when the
website is not open. The existing public website and Cloudflare Web Push monitor
are separate and remain active. No KRS-One audio is distributed.

## What is implemented in the development branch

- The native SwiftUI application bundles `xrp-alert.wav` and successfully
  compiles unsigned on a macOS GitHub Actions runner.
- The Apple delegate forwards APNs device tokens **only in memory** to the
  pairing model; the model never prints, caches or persists them.
- The native app uses a fixed HTTPS service origin. Its long-lived native
  bearer is kept in the iPhone Keychain using a this-device-only setting.
- The authenticated **existing web device** can issue a cryptographically
  random, one-time 256-bit pairing code valid for five minutes. The website's
  pairing controls are hidden unless the server says native pairing is enabled.
- Registration records and delivery queues use separate `cw-native-` storage
  prefixes. The existing Web Push subscription, VAPID keys, rules and
  authorisation are not changed or migrated.
- The APNs sender uses a bounded deadline and Apple ES256 token authentication.
  Its notification payload names the bundled `xrp-alert.wav` sound.
- Only **actual validated downward crossings** generated by the existing
  rule engine at $0.90, $0.80 or $0.70 are eligible. First observations,
  snapshots, gaps, stale observations and unrelated coins do not trigger.
- APNs queue writes are isolated from existing Web Push event commits, so
  failure to enqueue a native sound cannot block the original alert.
- Native device revocation is linked to the original web device's removal.

All cross-device delivery remains disabled in production until the steps below
are completed. The app's five-second local test does not prove APNs delivery.

## Prerequisites requiring the owner's Apple account

1. Enrol in or use an existing Apple Developer Program membership, if
   applicable. Membership is not purchased or changed from this project.
2. Register explicit App ID `com.jfaread.cryptowatch.sound` in the owner's
   Apple developer team, enable Push Notifications, and create appropriate
   development and distribution provisioning.
3. Sign and distribute the iOS application through the owner's Apple-approved
   route, typically TestFlight. Compile-only GitHub Actions is **not** an
   installable, properly signed iPhone build.
4. Create the APNs Auth Key in Apple's portal and record its Key ID and
   Team ID privately. Do not email or paste the `.p8` key into a chat or
   commit it to GitHub.

## Production activation - must be reviewed separately

The Cloudflare Worker code is **gated** by all the following settings:

- `NATIVE_APNS_ENABLED=true` - only after signing, security review and a real
  on-device enrolment test.
- `NATIVE_APNS_TEAM_ID` - exactly the authorised Apple team.
- `NATIVE_APNS_KEY_ID` - matches the private APNs signing key.
- `NATIVE_APNS_PRIVATE_KEY` - stored as a Cloudflare secret, never in source.
- `NATIVE_APNS_BUNDLE_ID=com.jfaread.cryptowatch.sound`.
- `NATIVE_APNS_ENVIRONMENT=sandbox` for signed development builds, or
  `production` for TestFlight/distribution.

**Do not activate or redeploy until** the existing ten Cloudflare bindings are
verified unchanged, the APNs key is in an appropriate secret store, and the
native code is reviewed. The original VAPID trio must not be replaced.
This staged branch does not change any live Worker settings or secrets.

The production site should then expose **Create one-time pairing code** only to
a connected web-alert device. On the installed iPhone app, enable
notifications, copy the pairing code from the website, paste it in the app
within five minutes, and pair. No audio file selection is required.

A real delivery check must cover the app open, screen locked, and app closed,
and verify that duplicate web/native alerts are acceptable or separately
suppressed. Verify the server's rules, delivery quotas and stored web subscriptions
before any production release.

**Important:** Apple's notification system can play the bundled sound on
native APNs alerts while the app is closed, but Silent Mode, Focus, notification
permissions and operating-system delivery restrictions still apply. This is
not a Critical Alert entitlement.

## Tests

The isolated workflow `.github/workflows/verify-native-xrp-sound.yml` builds
the app unsigned, compiles the Cloudflare Worker, runs the existing Web Push
regression suite and tests pairing, native event eligibility, mocked APNs
delivery, one-time codes, revocation and secrets not appearing in responses.
No genuine APNs notification or Apple account action occurs in those tests.
